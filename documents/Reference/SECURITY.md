# 보안 경계

현재 URL 구매 흐름의 보안 기준입니다. 코드 기반 보호와 실제 운영 환경 검증을 구분합니다.

변경일: 2026-11-12. [Linux 실행서](Deployment/LINUX_RELEASE.md)와 [국가별 개인정보 요구](COUNTRY_CUSTOMS.md)를 함께 적용합니다.

## 인증·권한

로그인 전 URL·분류·수량·옵션·도착국 확인은 순수 입력 검사와 안내, 일치하는 기존 공개 샘플의 날짜별 관찰 정보만 제공합니다. 상품 페이지 fetch·DB 접근·주문 생성·결제 연결은 수행하지 않으므로 게스트 입력이 유료 작업을 발생시키지 않습니다. 상품 초안은 같은 탭의 sessionStorage에 최대 4 KiB·24시간으로 보관하며 주소·통관 식별번호 필드는 받지 않습니다. 자유 입력 옵션에도 개인정보를 넣지 않도록 안내합니다. 실제 고객 API의 인증·소유권·할당량 검사와 분리합니다.

Supabase 서버 `getUser()`로 확인한 이메일 인증 계정만 배송정보 저장·구매 요청·개인 조회를 할 수 있습니다. 고객 ID와 운영자 여부를 본문·URL·브라우저 metadata에서 신뢰하지 않습니다.

공개 화면의 선택적 세션 갱신은 Auth 프로젝트 미설정·갱신 장애 때 화면을 계속 제공하지만 사용자를 인증된 것으로 취급하지 않습니다. 비공개 API는 자체 서버 인증을 계속 수행합니다.

고객의 읽기·취소·CS에는 요청 소유자를 함께 조회합니다. 운영자 권한은 DB `isAdmin`과 서버 운영자 설정으로 검증합니다. `/admin` 문자열은 권한이 아닙니다. 변경에는 필요한 역할을 요구하며 행위자와 출처를 남깁니다.

기존 order-intents GET은 게스트의 null 고객 ID가 전체 목록 필터로 이어질 수 있었습니다. 새 요청은 소유자 검증 경로를 사용합니다. middleware의 활성 API 목록 밖에 있는 모든 과거 API·cron은 DB 접근 전에 410을 반환합니다. 일부 과거 소스는 보존하며 과거 관리 화면은 구매 관리로 이동합니다. 기존 admin API 전부가 공개였다고 단정하지 않습니다.

## 개발 미리보기 경계

`/dev/preview`는 정확한 development 모드·서버 전용 `PAYNSHIP_DEV_PREVIEW=1`·localhost/loopback 조건을 모두 충족해야 합니다. production·플래그 비활성·외부 host는 404입니다. `X-Forwarded-Host` 같은 클라이언트 forwarding 값을 허용 근거로 사용하지 않습니다. 로컬 서버는 `--hostname 127.0.0.1`로 실행하고 외부 프록시·터널·공유 서버에 개발 모드를 공개하지 않습니다. host 검사는 네트워크 격리를 대신하지 않습니다.

미리보기 진입 시 마운트 후 같은 탭의 공개 상품 초안을 한 번만 읽으며, 4 KiB·24시간·strict schema 검사를 통과한 5개 필드만 사용합니다. 읽기 전용 저장소 연결은 원래 초안을 수정하지 않고 잘못됐거나 만료된 값도 삭제하지 않습니다. 유효한 초안이 없으면 빈 입력으로 시작하며 예제 상품은 명시적 선택으로만 입력합니다. 새로고침은 원래 공개 초안을 다시 읽을 수 있습니다.

이후 미리보기 변경과 화면 동작은 브라우저 메모리에 한정하고 strict 입력 스키마·샘플 2개를 포함한 최대 요청 20개·요청당 미해결 문의 3개를 적용합니다. 서버 DB·실제 고객 API·결제·배송 제공자를 연결하지 않고 인증 세션·운영자 역할도 발급하지 않습니다. 미리보기 내 로그인 상태도 실제 사용자로 위장하지 않습니다. `SAMPLE_ONLY` 배송 예시는 실제 이벤트로 취급하지 않습니다. 새로고침하면 변경·생성 요청·문의가 초기화됩니다. 관리자·결제·webhook 동작과 실제 API fallback은 제공하지 않습니다.

서버가 미리보기 요청을 검증해 전역 인증 provider의 Auth 호출을 비활성화하며 클라이언트가 보낸 미리보기 표시 header는 제거합니다. 진입·종료 시 전체 페이지 이동을 사용해 이전 root layout의 인증·메모리 상태를 이어받지 않습니다. 실제 고객 API는 미리보기 활성 여부와 관계없이 인증·소유권 검사를 유지하며 `/dev-login`을 복구하지 않습니다. 미리보기에는 실제 주소·통관 식별번호를 입력하지 않습니다.

## 개인정보·카드

신규 배송 프로필·구매 당시 배송 스냅샷·수취인/통관 검토·상품 옵션·이벤트 메모·CS 제목/내용/답변을 AES-256-GCM으로 암호화합니다. 자유 입력에 개인정보가 들어올 수 있기 때문입니다. PII_ENCRYPTION_KEY는 서버 전용 64자리 hex이며 레코드별 컨텍스트를 인증 데이터에 묶어 다른 레코드로의 암호문 교체를 감지합니다. 키 누락·변조·평문 신규 데이터는 진행을 중단합니다. 이미 평문으로 저장된 신규 데이터가 있다면 통제된 변환 계획이 필요하며 자동 덮어쓰지 않습니다.

목록에 DB 레코드를 통째로 직렬화하지 않고 상품·가격·상태·송장을 투영합니다. 개인정보는 권한 있는 상세 경로로만 반환하며 운영자의 개인정보 조회를 기록합니다. 로그에 비밀값과 전체 배송지를 출력하지 않습니다.

카드 번호, CVC, 카드 비밀번호는 앱 입력·DB·로그에 보관하지 않습니다. 외부 결제 페이지를 사용하며 결제 완료는 raw body 서명 webhook과 주문·금액·통화 확인으로만 반영합니다.

과거 `User.phone`, `UserPreferences.defaultAddress` 같은 보존 데이터가 자동 암호화되는 것은 아닙니다. 과거 데이터 점검·전환·삭제, 보존 기간, 고객 삭제 요청, 키 교체와 암호화 백업 복구는 출시 전 운영 과제입니다.

## 50,000건 제출·취소와 여러 서버

| 제한 | 현재 초기 값 |
| --- | --- |
| 변경 API JSON body | 8 KiB |
| 한 요청의 URL | 1개, 최대 2,048자 |
| 수량 | 1–10개 |
| 계정 제출 | 하루 20회 |
| 활성 요청 | 계정당 최대 5개 |
| 전체 제출 | 하루 1,000회 |
| 고객 직접 취소 | 하루 5회 |
| 배송정보 저장 | 하루 20회 |
| CS 문의 생성 | 하루 10회, 요청당 미해결 최대 3건 |

할당량은 PostgreSQL에 기록하고 생성·취소와 같은 트랜잭션으로 처리합니다. DB Serializable 격리와 제한된 재시도로 여러 서버의 경합을 제어합니다. UUID 제출 키와 payload hash로 같은 제출 재시도는 같은 결과를 반환하고, 내용이 다른 키 재사용은 거절합니다. 상태 변경에는 `version` 조건을 넣습니다.

이 제한은 인프라 DDoS 또는 다수 계정 생성을 전부 해결하지 않습니다. 공개 운영에는 공유 Redis 요청 제한, 신뢰 가능한 프록시 IP 설정, edge/WAF·봇 억제, 비용 경보와 운영 정지 절차가 필요합니다. 실제 부하 시험 없이 전 세계 동시 접속 검증 완료로 표시하지 않습니다.

production 요청 제한기는 Redis 장애·설정 누락 시 일반 API를 503으로 차단합니다. 세션 변경 요청은 정확한 앱 origin을 검사하고 body를 스트림 한도로 읽습니다. liveness GET /api/health는 DB·Redis 확인 없이 응답하며 deep 검사는 operator 인증 뒤 DB만 확인합니다. 점검 모드는 DB의 실제 설정을 읽어 신규 접수·checkout을 중단합니다.

## URL·webhook·상태

정확한 HTTPS 판매처 host·상품 경로만 받고 사용자 정보·포트·임의 host를 거절합니다. 고객 제출 API는 페이지를 fetch하지 않습니다. 별도 운영자 상품 증거 CLI는 같은 URL 정책과 DNS/리디렉션·timeout·응답 크기·robots 제한을 사용하며 고객이 일괄 호출하는 공개 endpoint가 아닙니다. 수집 성공은 통관 승인으로 사용하지 않습니다.

자동 HS 분류와 추정 세율을 제거합니다. 검토를 통과한 견적만 결제 대상이며 수취인 형식 검사와 증빙 확인을 구분합니다. 고객·운영자는 PAID를 직접 지정하지 못하고 provider 대조로만 결제를 확인합니다. 배송은 raw body HMAC·5분 전송 범위·송장 소유권·provider별 중복 receipt·이벤트 시간 순서를 검증합니다. DELIVERED는 서명 배송 이벤트로만 반영합니다.

## DB와 검증 범위

신규 SQL은 6개 새 테이블과 54개 보존 앱 테이블의 RLS 활성화와 anon/authenticated/PUBLIC 테이블 권한 회수를 포함합니다. 기존 정책을 일괄 삭제하지 않으므로 실제 DB에서 정책·컬럼 권한·역할 상속을 조사하고 브라우저 접근이 남아 있으면 출시를 중단합니다. 원격 DB의 기존 상태를 조사하지 않았으므로 실제 과거 유출이나 SQL 적용 완료를 주장하지 않습니다. 출시에는 SQL 적용과 실제 REST·DB 역할 검증이 필요합니다.

런타임 역할은 NOSUPERUSER·NOBYPASSRLS·비owner이고 신규 업무에 필요한 테이블과 users email·운영 설정 컬럼만 변경합니다. 관리자 is_admin은 앱이 생성/수정할 수 없습니다. RLS의 서버 정책은 명시적 paynship_app 역할에만 허용하고 고객별 소유권은 서버 API에서 검증합니다. [권한 SQL](../../deploy/linux/runtime-role.sql)

GitHub CI의 임시 PostgreSQL 16 smoke는 DB 권한·RLS·제약과 정상 CRUD를 검증하며 fixture를 rollback합니다. 코드 commit 4c9874b의 실제 Linux CI가 통과했으며 SHA·실행 링크는 [검사 기록](Testing/SECURITY_CHECKS.md)에 있습니다. 로컬 단위 검사·비로그인 ZAP는 인증된 소유권·실제 DB 병렬 처리·provider 정산·복구를 증명하지 않습니다. ZAP 결과는 실제 스캔 범위와 별도로 기록하며 출시 전 고객 2계정·운영자 역할·공유 Redis·실제 제공자 통합을 검증합니다.

2026-10-12 실행한 ZAP의 CSP 중간 위험을 수정하고 53 URL을 재검사했습니다. 높음/중간 0건, 낮음 redirect 4건과 정보 경고가 남았습니다. 실제 검사·제외 범위와 잔여 항목은 [검사 기록](Testing/SECURITY_CHECKS.md)을 확인합니다.


## 계정·게스트 표현 변경 (2026-11-12)

이메일 가입/로그인은 Supabase Auth를 사용하고 비밀번호를 앱 데이터베이스나 로그에 저장하지 않습니다. 서버 callback은 교환 후 사용자·확인 이메일을 재검증하며 내부 허용 경로로만 복귀합니다. 이메일·Google·Apple·Naver는 HTTPS 또는 정확한 loopback 개발 origin만 허용하고 일반 HTTP IP 입력·동작을 막습니다. 계정·callback 경로는 private, no-store입니다. 게스트 요청/주소 화면은 정적 설명·예시만 표시하며 기존 고객 API의 사용자·소유권·암호화·할당량 검사는 그대로 유지합니다. 기존 Supabase demo 테이블의 synthetic 공개 데이터와 고객 개인정보는 분리합니다.

Google·Apple은 내장 Supabase OAuth, Naver는 `custom:naver`를 사용합니다. Apple·Naver 공개 활성화 플래그는 UI 설정일 뿐 인증 증거가 아닙니다. 제공자 Client Secret과 Apple 서명 키는 브라우저 변수에 넣지 않으며 Naver Client ID/Secret은 Supabase에만 설정합니다. Apple 웹 로그인 secret의 만료·교체를 운영 일정으로 관리합니다.

`GET /auth/naver/userinfo`는 서버 플래그가 켜졌을 때만 Naver Bearer 토큰을 받아 고정 HTTPS 프로필 endpoint에 전달합니다. 임의 fetch·리디렉션·사용자가 지정한 host를 허용하지 않습니다. 토큰/응답 크기·timeout·공유 요청 제한을 적용하고 production Redis 장애는 차단합니다. 반환값은 확인한 Naver ID와 이메일, `email_verified: false`로 한정하고 프로필·토큰의 저장/로그·DB 접근·세션 발급은 수행하지 않습니다. 이 경로는 Supabase의 서버 간 프로필 조회용이며 고객 API 인증을 대체하지 않습니다.

Naver 프로필의 이메일을 자체적으로 검증됐다고 간주하지 않습니다. Supabase Confirm email을 켜고 확인 메일 발송을 구성해야 합니다. `provider_email_needs_verification`은 확인 안내로 처리하고 확인 전 개인 기능은 거절합니다. 주소·계정 연결 권한을 브라우저의 provider 이름이나 이메일 문자열만으로 부여하지 않습니다. 실제 제공자 연결과 확인 메일 검증은 배포 환경에서 별도로 수행합니다.
