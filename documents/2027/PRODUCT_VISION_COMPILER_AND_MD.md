# PayNShip 제품 헌장 — 역직구 컴파일러 + MD

> **<u>우리가 만드는 것은 한국 상품을 대신 사서 보내는 단순 역직구 사이트가 아니다. 상품 URL과 고객의 구매 의도를 입력받아, 해당 국가에서 합법적으로 구매·통관·수령할 수 있는 실행계획과 검증 가능한 총도착가격으로 변환하는 '역직구 컴파일러(Cross-Border Commerce Compiler)'다.</u>**
>
> **<u>MD(Merchandising)는 이 컴파일러 위에서 수익을 만드는 발견·선정·추천·재방문 엔진이다. 컴파일러는 '어떻게 안전하게 살 수 있는가'를 해결하고, MD는 '왜 여기서 무엇을 사야 하는가'를 해결한다.</u>**

**우선 적용되는 사업·제품 방향 문서.** 작성 2026-11-22. **목표이며 구현완료가 아님.** 이하 모든 SRS/테스트/화면/데이터 변경은 이 문서와 부합해야 한다. 코드 변경은 별도 단계.

## 1. 제품을 잘못 이해하지 않도록 하는 정의

### 1.1 컴파일러 비유 — 실제 기능 대응

| 컴파일러 개념 | PayNShip이 반드시 해야 할 일 | 고객에게 보이는 결과 |
| --- | --- | --- |
| Source code | 네이버/무신사/다이소/기타 한국 쇼핑몰 URL, MD에서 고른 상품, 옵션·수량·배송국가 | 링크/상품·옵션·수량 선택 |
| Lexer / Parser | URL·판매처·모델·상품번호·SKU·색상·사이즈·통화·가격·재고 구조화, 출처 보관 | 확인된 제품 정보와 누락 정보 |
| Semantic analysis | 원산지·재질·용도·성분·배터리 등과 국가별 HS 세번·수입제한·수취인/수입자·통관절차의 정합성 검사 | 구매/배송 가능 상태, 제한 사유 |
| Type checking | 미국/일본/중국의 통관 방식·품목분류·허가·DDP 지원 자격·증빙 신선도 검증; 불명확하면 오류/검토 상태 | '확인 후 견적', 필요한 확인사항 |
| Intermediate Representation (IR) | 상품별 검증증거 + 수입국·실제 제조국 + 정책 버전 + 수량 + 과세가격 구성 + 배송 제약을 담은 **불변 Trade Plan** | 사용자는 내부 계획을 직접 편집하지 않음 |
| Optimization | 허용된 소싱처, 한국 내 물류, 3PL, 합배송/분할배송, DDP 가능 운송 경로, 비용·기한·법적 제약을 비교 | 총 배송비, 검증된 합배송 절감액, 예상 도착일 |
| Code generation / execution | 구매 실행 → 입고·검수 → 통관 데이터/서류 준비 → 적법한 운송사/통관사 인계 → 배송 추적 → 환불/사후처리 | 주문 확정과 실측 기반 상태 추적 |
| Diagnostics | URL 추출 실패·제조국 불명·통관불가·배송 불가·세금 불명·가격 변동에 원인코드와 복구 행동 | 사람이 이해할 수 있는 오류/다음 단계 |

**이것은 컴파일러 개념을 차용한 오케스트레이션 아키텍처이며, 독자적 세관 신고 권한이 생긴다는 의미가 아니다.** 세관 신고와 DDP 실행은 적법한 수출자·수입자·브로커·운송사 계약 및 증빙을 전제로 한다.

### 1.2 고객/내부 책임의 분리

| 고객에게 기본 UI에서 선택시키지 않을 것 | 고객에게 필수로 보여줄 것 |
| --- | --- |
| 배대지 주소·창고·3PL 선택 | 실제 근거에 따른 예상 도착 범위 또는 확인 중 |
| EMS/DHL/FedEx 등 배송사별 요금 비교와 라우팅 결정 | 총 배송비, 포함/제외 항목과 도착 시 추가 청구 가능성 |
| 합배송/분할배송 최적화 알고리즘 | 검증된 조건에서 절약한 금액; 지연이 발생하면 고지 |
| 내부 구매처·상품 소싱 우선순위 | 정품 검증 근거와 정확한 상품/옵션/수량 |
| HTS/HS 코드 선정 단계·신고서 생성 절차 | 수입 가능 여부, 관세·세금·통관비, 누가 부담하는지 |
| 창고 반품/구매처 협의 작업 | 취소·환불 조건, 신청/진행/처리 결과 |

신원·통관 위임·동의·세금·법적 책임은 숨기지 않는다. 고객은 운송사를 **고를 필요**는 없지만 송장으로 조회할 **권리**는 있다. 검증되지 않은 예측값을 사실처럼 표시하지 않는다.

### 1.3 반례: 이런 구현은 성공이 아님

- URL에서 제목·이미지만 파싱하고 '상품 인식 성공'으로 표시.
- 고객에게 미국 HTS 코드, 중국 CBEC 유형, 배송사를 직접 선택하도록 요청.
- HS6만 알고 세부 분류·원산지·운송비 검증 없이 '관세 포함' 결제 허용.
- 고객에게 상품 구매가+15%만 표시하고 해외 배송비·수입세는 추후 청구.
- 로그인 고객에게 새 상품만 보여주고 진행 중인 주문을 찾도록 여러 번 클릭 요구.
- 한국 나이키 할인율이 높다는 이유만으로 '미국보다 저렴' 표시.
- 실제 검증되지 않은 ETA, 절약액, 배송완료 이벤트, 관세 0원 생성.
- 중국 국제택배를 CBEC라고 가정하여 우대세율 자동 적용.

## 2. MD가 컴파일러와 결합되는 사업 모델

MD는 부속 홍보 배너가 아니라 **검증된 컴파일 결과를 상품 진열의 판단 근거로 사용하는 상거래 엔진**이다.

### 2.1 두 진입점, 하나의 컴파일러

**A. 고객 주도 구매(의도 기반):** 고객이 URL/상품명/옵션/수량/국가를 입력 → Parser → 증거 확보 → Semantic/Compliance → 물류 최적화 → 견적/구매/추적.

**B. MD 주도 구매(발견 기반):** 운영자가 한국 상품을 후보로 수집 → 같은 컴파일러로 국가별 판매 적격성과 총도착원가를 **미리 계산·승인** → 해당 국가 고객에게 큐레이션 → 고객은 수량/옵션만 선택 → 결제 직전 새 데이터 재검증 → 같은 구매/배송/추적.

**컴파일 엔진은 정확히 하나**다. MD 전용 가짜 관세, URL 구매대행 전용 별도 관세, 국가별 화면 하드코딩 금지.

### 2.2 MD가 실제로 수익을 얻는 구조

- 수익: 투명한 서비스 수수료(현재 신규 주문 상품 소계 15%, 최소 수수료 없음), 합법적이고 고지된 소싱/물류 개선으로 발생하는 운영 효율, 승인된 부가 서비스.
- 지출: 실제 매입, 국내배송, 창고·검수·포장, 국제운임, 세금/통관, 결제/환전, 파손·반품·재배송, 고객지원.
- **매출총이익과 합배송 절감액을 혼동하지 말 것.** 고객에게 표시한 절감액과 운영상 원가 절감/마진을 따로 기록한다.
- 선정 후보: K-pop 앨범/공식 굿즈, 문구/서적, 한국 한정 패션·소품, 조건이 검증된 K-뷰티; Nike/Adidas 등 정품 재고할인품은 정확한 SKU·색상·사이즈·제조국과 미국/중국 현지 **동일 SKU** 실판매가 비교 후 후보화.
- '한국에서는 인기 없는 아재 스타일'은 검증되지 않은 해석일 뿐 데이터 규칙으로 쓰지 않는다. 실측 구매전환율·재고기간·가격차·반품률과 현지 사용자 반응으로 검증.
- MD 추천 점수 입력: 목적국 법적 배송 가능(하드 게이트), 재고/가격 증거 신선도, 국가별 최종 소비자가 차익, 희소성 근거, 예상 주문 기여이익, 배송/환불 위험, 관심 카테고리.
- MD 목표지표: 국가별 상품 노출→선택→견적완료→결제→성공배송 전환, 재구매율, 주문당 기여이익, 배송 정시율, 관세/배송 예측오차. '체류시간'은 보조지표, 구매 완성률보다 앞세우지 않는다.

**현행 부족 사항:** 8개 고정 MD 목록, 국가별 진열/추천 근거 부족, SKU·정품·현지 가격 비교, 국가별 세관/배송 검증 상태, 다국어 카피, 주문 상태와 MD의 연계, 실시간 가격증거 갱신이 부족. MD 상품을 늘리기 전에 **고객에게 볼 수 있는 정보의 품질**을 올려야 한다.

### 2.3 Delivered Korea에서 배울 점과 넘어설 지점

공개 서비스 https://www.delivered.co.kr/en/we-buy-and-ship 에서 확인 가능한 범위: 한국 구매대행 URL 요청, 자동 정보 로딩 시도, 실패 시 수동 요청, 구매팀 견적, 보관·합배송·배송/환불/금지품목 가이드. 실수요 국가별 점유율은 공개 근거 없이 단정하지 않는다.

| Delivered Korea 참고 | PayNShip의 명확한 개선 목표 |
| --- | --- |
| URL 자동 입력 실패 시 manual request | 어떤 필드가 수집/미수집인지, 왜 최종 견적이 막혔는지 표시하는 **컴파일 오류 진단** |
| 한국 창고/국제배송 단계와 선택지 | 창고·배송사 선택은 내부 컴파일 최적화, 고객은 가격·배송일과 추적만 |
| 여러 단계에서 구매·배송 결제 | 합법적 DDP 지원 노선에서 도착 총액을 사전 확정하려는 경험; 불가 시 투명한 보류/동의 |
| 합배송 지원 | 각 대안의 실제 총비용·지연·수입규정을 비교해 **검증된 절감액** 표시 |
| 배송 안내·반품/금지품목/FAQ | PayNShip 자체의 국가·상품별 서비스 가이드, 일정·비용·취소시점·예외 처리 |
| 한국 상품을 대신 구매 | **컴파일러의 자동 검증 능력 + MD의 판매 가능 국가별 큐레이션** 결합 |

타사의 비공개 코드를 복제하거나 robots/접근제어를 우회하지 말 것. 실제 URL 수집은 적법한 제휴/공식 피드/허용 HTML/운영자 검토 순으로 접근한다.

## 3. Compiler IR: 개발자가 먼저 결정할 데이터 계약(개념 수준)

TradePlan에는 `orderIntent{sourceUrl,merchantProductId,sellerSku,brandModel,color,size,qty,destination}`, `productEvidence{field,observedValue,source,observedAt,confidence,approvedAt}`, `tradeIdentity{sellerCountry,dispatchCountry,manufactureOrigin,hs6Candidate,nationalTariffCode,regime,importerRole}`, `regulatoryDecision{status,reasonCode,ruleVersion,effectiveDate,approver}`, `costBreakdown{merchandise,fee,domesticShip,warehouse,internationalShip,duty,additionalDuty,tax,clearance,insurance,payment,fx}`, `fulfillmentPlan{sourcePurchase,warehouse,consolidation,carrier,incoterm,deliveryWindow}`, `proof{quoteSnapshot,customsEvidence,trackingEvents}`가 분리되어야 한다.

이것은 외부 API가 아니라 **내부적으로 독립 시험할 수 있는 중간 표현(IR)**이다. 특정 REST API나 마이크로서비스 추가가 목표가 아니다. 기존 Next.js 서버 로직에 순수 함수, 안전한 DB 기록, 이벤트 연계로 구현 가능하다. 원본 가격/환율/세칙의 공식 출처와 버전이 없으면 `TradePlan`의 상태는 `NEEDS_EVIDENCE`이며 결제 불가.

### 단계별 출력 계약

| Phase | 성공 증거 | 오류 시 처리 |
| --- | --- | --- |
| Parse | 정확한 판매처 상품 ID와 옵션/수량 | MANUAL_REQUEST |
| Enrich | 실제 제조국/재질/용도/옵션별 가격/중량 출처 | MISSING_PRODUCT_EVIDENCE |
| Classify | HS6 후보 + 목적국 승인 국별 세번 | UNCLASSIFIED |
| Validate | 국가/품목/통관방식/수취인·수입자 적합성 | RESTRICTED/REVIEW_REQUIRED |
| Estimate | 합법적인 평가가격/세목과 실제 운임/환율 근거 | CHARGES_UNKNOWN |
| Plan | 수입규정을 지키는 DDP 또는 명시 동의 DAP 경로 | ROUTE_UNAVAILABLE |
| Commit | 고객이 선택한 정확한 상품·총액·약관 동의·서버 승인 | QUOTE_EXPIRED/PRICE_CHANGED |
| Track | 실제 창고·운송사 이벤트 및 본인 주문 | ACTION_REQUIRED/STALE_TRACKING |

## 4. 국가별 Compiler Plug-in: 동일 인터페이스, 다른 법

**국가별 규칙은 관세만이 아니다.** US: HTSUS10·원산지별 관세/추가조치·CBP 수입방식·FDA/CPSC/FCC 관련 규제·DDP 운송사 계약. JP: 일본 9자리 분류·우편/특송/일반화물·관세/국가 및 지방 소비세·개인/상업 수입·약기법/PSE 등. CN: 개인우편/CBEC/일반무역을 구별하고 포지티브 리스트·한도·결제/물류 자료·현지 통관사와 DDP 가능성을 검증. 세 국가 모두 **법령 시행일별 버전**과 출처/승인자 저장. 2027 세율을 정적 상수로 생성하지 않는다.

국가 컴파일러는 `classify -> verifyAdmissibility -> assessValue -> calculateDutiesAndTaxes -> verifyImporterAndCarrier -> produceTradePlan`의 공통 결과 타입을 제공한다. '지원 국가'는 이름만 드롭다운에 있다는 뜻이 아니라 실제 승인된 상품군 × 수입 방식 × 운송사 노선이 있다는 뜻이다.

정확한 SW 요구사항과 Golden Test: [INTEGRATED_SRS.md](INTEGRATED_SRS.md), [TEST_MATRIX.md](TEST_MATRIX.md). 구체적인 화면/MD/환불 안내: [UX_MD_AND_SERVICE_GUIDE.md](UX_MD_AND_SERVICE_GUIDE.md).

## 5. 고객 경험과 언어

**Guest:** 중국어 간체/영어 등 현지 고객용 MD + URL 입력 → 상품 상세(확인된 정보 vs 모르는 정보) → 선택한 국가·옵션·수량에 따른 총도착액 또는 '검토 필요' → 로그인은 주문 저장/배송지/결제 시점.

**Login + active order:** 첫 화면에서 **내 주문이 어디에 있고 언제 올지**, 통관 보류 또는 고객 액션, 실제 이벤트 시각을 표시. MD는 계속 아래에 제공. **Login + no order:** MD/URL 우선. 배송 선택을 강요하지 않음.

중국어 예: **“发现韩国好物，选好商品，其余交给 PayNShip。”**  
영어 예: **“Discover Korean products. Choose what you want; we handle the rest.”**  
DDP 지원이 검증된 상품/국가만 ‘Duties and taxes included’ 또는 ‘税费已包含’ 표시한다.

## 6. 컴파일러 품질 테스트(기능별 테스트의 상위 계약)

1. **Parser test:** 같은 상품 URL인데 색상·사이즈가 다르면 서로 다른 variant fingerprint, 상품명만 가져오면 부분 성공.
2. **Semantic test:** 한국 판매처의 베트남 제조 폴로는 제조국 VN 유지, 원산지 불명은 국별 분류/결제 보류.
3. **Country plug-in test:** 동일 상품을 US/JP/CN으로 바꾸면 HS 국별코드/수입 방식/세금·규제 판단이 별개.
4. **Compiler error test:** HS6만 있거나 추가 관세 근거 만료 → 고객 화면에서 검토 필요/이유, **절대 관세 0원 자동 치환 금지**.
5. **DDP test:** 유효한 운송사 DDP 계약·수입자·세액 확인이 있을 때만 결제/포함 표시; 없으면 보류 또는 승인된 DAP.
6. **Optimization test:** 합배송 실 운임·포장/보관료·부피무게·통관·기한까지 비교, 음수 절감액에는 절약 배지 금지.
7. **MD integration test:** URL 입력과 MD 카드가 동일 컴파일 엔진 사용, MD 할인 배지는 동일 SKU 현지 실가·총도착가 근거 없으면 차단.
8. **Tracking test:** 본인 계정 주문만, 서명된 배송완료, 다중 박스 일부 완료는 전체 완료 아님.
9. **Lifecycle test:** 견적→구매→출고 직전 변경된 원산지/관세/규정/환율을 재검증, 결제 이력 불변.
10. **Real-world golden vector:** 미국·일본·중국의 실제 관세사/운송사로 승인받은 `상품+원산지+코드+수입 방식+법령일+평가가격+세목+통관비`를 테스트 기준으로 저장하고 100% 일치해야 해당 노선 활성화. 가짜 세율 fixture로 시장 출시 승인 금지.

## 7. 에이전트에게 내리는 실행 지침

**<u>개발 방향을 바꾸지 말 것: 먼저 고객이 보는 '완성된 구매 결과'를 정의하고, 이를 만들기 위한 Compiler Phase를 역으로 설계하라.</u>**

- **이 문서가 사업/제품 방향의 최상위 소스다.** 기존 구현과 충돌하면 현행 코드를 파괴하지 않고 차이를 정리한 뒤 요구사항별 점진 수정. 기존 결제·PII·운송장 증거·과거 유료 견적은 보존.
- **Day 0/과도한 자체 점검 프레임과 API 신설 자체를 목표로 삼지 말 것.** 실행할 작업은 ① 상품 분석 결과 표시 ② 통관용 상품 ID/원산지/HS/규제 정보 확보 ③ 고객 견적과 DDP ④ 로그인 주문 추적 ⑤ MD 검증/진열 ⑥ 합배송/비용 최적화 순서로 나눌 수 있으나, 각 기능은 같은 컴파일러를 공유해야 한다.
- 개발자가 모르는 미국/중국/일본 품목 관세율, 세관 식별번호, DDP 계약과 실제 운임을 **조사·증거화할 작업**으로 남긴다. 외부 증빙이 없으면 실패를 드러내는 UI/DB/테스트를 개발하되 고객에게 확정 가격으로 판매하지 말 것.
- PR은 고객 화면의 Before/After, 단순 제목 파싱에서 무엇이 달라졌는지, 각 국별 통관 코드/세목의 근거, MD의 사업적 편익, 검증된 Golden Test와 미검증 항목을 보고해야 한다.
- **완료는 코드가 빌드된 것이 아니라:** 고객이 상품을 고르면 합법적으로 살 수 있는 국가·총비용·배송예정 또는 검토 사유가 이해 가능하게 나타나고, 로그인 후 자기 주문의 실제 상태를 추적할 수 있으며, MD가 같은 검증 기준으로 상품을 제안하는 상태다.
