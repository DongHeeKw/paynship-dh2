# PayNShip 개발 헌장: TDD-first, Agent Autonomous, Human Learning

> **<u>사용자가 Three.js/Next.js/Prisma/DB를 사전에 리뷰할 수 없다는 것은 결함이 아니라 개발 프로세스의 핵심 제약이다. 기술 구현 승인 요청을 사용자에게 반복하지 말 것. 에이전트가 명시된 제품 요구사항에 근거해 설계·구현·검증하고, 사용자는 단계별 결과물과 예제를 공부하며 따라간다.</u>**
>
> **<u>PayNShip = 역직구 컴파일러 + MD 성장 엔진. 실제 구매처·자택 Home Hub·합배송·국별 관세·DDP·해외 운송의 알고리즘과 테스트가 UI 장식보다 우선한다.</u>**

**적용 범위:** PayNShip 코드/테스트/DB/Next.js/Three.js/CI/문서의 변경. 2026-11-22. 타 저장소는 개별 제품 요구사항/접근 범위 확인 없이 일괄 수정하지 않는다.

## 1. 사용자의 역할 vs 에이전트의 역할

| 항목 | Agent가 직접 결정하고 입증 | 사용자에게 전달할 것 | 사용자에게 판단을 넘기면 안 되는 것 |
| --- | --- | --- | --- |
| 코드 구조/함수 분리 | 책임과 테스트가 분명한 모듈 구성 | 입력·출력·의존성 설명 | 파일명, TS 타입, ORM 쿼리 구현방식 |
| Next.js/React/Three.js | 접근성·성능·선언적 컴포넌트 설계 | 변경 전후 스크린샷/재현 절차 | useState/useEffect, 렌더링 기술 선택 |
| DB/마이그레이션 | 기존 스키마 호환·데이터 보존·롤백 설계 | 테이블 관계 그림과 데이터 예시 | FK/인덱스/Prisma 내부 구현 승인 |
| 알고리즘 | 정상/오류/경계 TDD, 계산 근거 | 샘플 입력→예상 선택 이유·금액·대기일 | 정렬/휴리스틱 선택에 대한 비전문가의 허락 |
| 서비스 품질 | 실제 테스트/CI/보안/성능 근거 | 성공·실패·미검증 범위 | "코드 봐서 문제 없는지 승인" 요청 |
| 운영·법률·금전 | 계약의 법적 영향 설명, 필요 승인 체크 | 수입자 책임·사업자 계약·비용·고객 고지 | 실제 외부 계약·세관신고·유료결제에 대한 임의 승인 |

**예외:** 법률상 신고주체·사업자계약·개인정보 공개·실제 고객에게 돈 청구·환불/제품 실제 구매·배포 같은 외부 효과는 개발 에이전트가 마음대로 결정해선 안 된다. 기술 구현은 자동 진행하되 외부 변경은 검증된 승인/계약을 갖춘 경우에만 실행.

## 2. 코드 품질: 제공된 두 참고 글을 PayNShip 규칙으로 변환

참고: https://toss.tech/article/frontend-declarative-code 및 https://frontend-fundamentals.com/code-quality/code/

- **선언적:** 컴포넌트는 '무엇을 보여줄지'를 표현. 예: \`<ConsolidationSuggestion savings={...} extraWaitDays={...} />\`. 내부 요금 계산, 통관 코드 분류, 권한 조회는 컴포넌트 이벤트 핸들러 안에 섞지 않는다.
- **가독성:** 함수/테스트 이름이 비즈니스 개념을 설명한다(\`isDDPAvailable\`, \`chooseLeastCostEligiblePlan\`). 어려운 조건은 명명된 predicate로 분해, 긴 복합 삼항연산 금지.
- **예측 가능성:** 동일 입력→동일 출력인 순수 엔진 함수. \`UNKNOWN\`, \`NEEDS_REVIEW\`, \`VERIFIED\` 타입을 명확히 하고 null을 0으로 바꾸지 않음. 날짜/환율/실운임은 외부 시각/스냅샷 인자로 받아 숨겨진 \`Date.now()\` 의존 없애기.
- **응집도:** HS/관세 계산은 trade, 요금은 carrier, 합배송은 consolidation, MD 큐레이션은 catalog. 함께 변경되는 세율/버전/골든 테스트를 가까운 곳에 둔다.
- **결합도:** 엔진은 Next.js route/UI/Prisma client/Three.js import 금지; 입력 DTO·출력 결과로 연결. React는 선언적 프레젠테이션, DB는 persistence adapter. 필요 없는 과잉 추상화·마이크로서비스 금지.
- **테스트 가능:** 상품명 파서가 HS10을 즉석에서 생성하거나 UI에서 관세를 계산하지 않는다. 외부 API·브로커·배송사 데이터 없을 때 deterministic fixture로 순수 알고리즘을 먼저 검증한다.
- **숨긴 비용 금지:** 15% 서비스 수수료(현재 신규견적 최소 없음), 국내/해외 운임, 관세/세금, 통관/보험/환불 비용은 분리해 증명. 합배송으로 회사 내부 수익이 늘었다고 이를 고객 절감액으로 표시하지 않음.

두 글의 원칙은 "추상화를 많이 하면 좋다"가 아니라 **바뀔 부분을 쉽게 수정하고 책임을 예측할 수 있게 하라**는 관점으로 해석한다. 해당 사이트의 원문/코드 복제 대신 링크·실제 적용 규칙을 작성한다.

## 3. TDD 실행 계약 — RED → GREEN → REFACTOR

### RED: 사업 규칙 테스트부터

1. 가장 작은 사용자 가치를 지정: 예) "다른 고객 주문을 합배송하지 않는다", "3일 기다리면 8,000원 절약 제안", "DDP 없는 저가 배송사 후보 제외".
2. 입력 fixture / 예상 출력 / 오류 상태 / 이유를 문서와 테스트에 동시 기록한다.
3. 해당 테스트만 실행해 **실패 확인**하고 콘솔 로그를 PR에 첨부한다. 아직 실제 실행이 불가능하면 "RED NOT VERIFIED"로 남긴다.
4. AI가 예상 통관율·관세사 승인·운송사 실요금을 임의 생성해서 RED를 통과시키면 안 된다. 샘플 운임은 \`SYNTHETIC_TEST_DATA\`로 분리한다.

### GREEN: 가장 작은 실제 구현

1. 외부 I/O 없는 순수 로직부터 코딩, 입력·출력 타입 명시.
2. 하드 게이트(동일 수취인/주소, 제한 품목, 유효한 요금과 세칙, DDP 계약, 배송 SLA)부터 적용하고 적격 후보만 최저원가 비교한다.
3. mock carrier 데이터와 실제 계약 carrier 데이터를 구분한다. 실데이터 미확인 단계에서는 \`REVIEW_REQUIRED\`.
4. 테스트가 통과하는 최소 구현만 제출. 테스트를 코드에 맞게 약화시키지 않는다.

### REFACTOR: 같은 행동·더 읽기 쉬운 코드

1. 중복 규칙, 복잡 조건, DB/UI 결합을 분해; 의미 있는 이름/반환형 통일.
2. 재실행하여 **기존 테스트 및 신규 테스트** 모두 유지되는지 확인.
3. 사용자에게 "왜 이 파일이 생겼고, 어떤 값을 바꾸면 무엇이 변하는지"를 설명한다.
4. 모듈 설계 의도가 바뀌면 ADR/기록 남기기.

**증거 규칙:** RED/GREEN/REFACTOR 실제 실행로그·commit을 확인하지 않았다면, TDD 순서대로 작업했다고 주장하지 않는다. \`npm run type-check\`, \`npm run test:ci\`, \`npm run build\`, \`npm run docs:check\`, 영향받는 Playwright 테스트를 실제 실행해 결과를 기록한다. 도구에서 실행할 수 없는 경우 정확히 \`NOT RUN\` 표시.

## 4. 개발 흐름: 사용자는 각 단계의 결과를 공부

단계가 끝나면 \`LEARNING_LOG.md\` 또는 PR 설명에 아래 형식으로 한국어 기록.

| 항목 | 필수 내용 |
| --- | --- |
| 비즈니스 문제 | 고객은 무엇이 불편했는가? (예: 분할배송으로 22,000원 더 지출) |
| 기능 변화 | 변경 전/후 고객/운영자에게 보이는 결과 |
| 테스트 먼저 | 테스트 이름/데이터/예상 결과/실제 RED 로그 |
| 구현 파일 | 딱 3~5개 핵심 파일과 각 한 줄 책임 |
| 왜 이렇게 구현? | 요구사항→순수 함수→결과/상태→React/DB 연결 이유 |
| 실행 방법 | 저장소 루트 명령, 샘플 데이터, 기대 출력, 초기화 방법 |
| 리팩터링 | 변경 전후 코드 가독성의 실질적 개선 |
| 실패/제약 | 실제 통관/요금/고객 데이터 연결 여부, 아직 막히는 이유 |
| 사용자 학습 | 먼저 이해할 용어 3개, 코드 읽는 순서, 한 가지 작은 실습 |
| 완료 판정 | 테스트 통과/미실행/실연동 미검증을 분리해 표기 |

**사용자 체크포인트**는 승인 권한 행사가 아니라 "화면을 켜서, 3일 기다리면 8,000원이 절약된다는 뜻을 이해하고, 코드에서 어디서 그 숫자가 결정되는지 학습"하는 것.

## 5. 사용자 질문으로 개발을 멈추지 않는 우선순위

- 결정이 없어도 안전하게 진행할 수 있는 코드는 에이전트가 직접 구현: 타입/테스트/순수 알고리즘/로컬 샘플/설명/접근성/모듈/DB additive migration.
- 승인이나 실제 외부 데이터가 없는 부분은 승인 전용 gate를 만든 후 다음 안전한 작업으로 이동: 고객 실제 구매, Shopify live 청구, 자택 주소 노출, DDP 표시, 브로커/캐리어 계약, 법정 통관 신고.
- 이미 알려진 사업 방향(집=HOME_HUB, 3PL은 후속, MD+URL 동일 컴파일러, US/CN/JP, 15% 신규 서비스 수수료, 초보자 학습 경험)을 다시 질문하지 않는다.
- 기술적 질문에는 테스트 가능한 두 안을 비교해 **에이전트가 근거를 남기고 선택**한다.
- 기능 동작을 바꾸지 않는 구조적 개선은 과도한 리팩터링보다 현재 다음 테스트에 필요한 범위로 제한.

## 6. 절대 깨뜨리지 말아야 할 기존 특성

- 기존 \`PurchaseRequest\`/결제 이벤트·고객 주문·과거 유료 견적을 마이그레이션/수정 중 손상 금지.
- 기존 결제 제공자 서명·고객 소유권 검증·PII 암호화·관리자 권한·운송사 서명 이벤트/배송 완료 검증 유지.
- 기간 지난 관세 근거를 임의 갱신해 출고 통과시키지 않음.
- 미확정 duty, international rate, DDP fees를 자동 0 처리하지 않음.
- 자택 주소를 공개 상품 API나 스크린샷/샘플 DB에 넣지 않음.
- MD의 나이키/아디다스 "미국보다 싸다" 주장은 동일 SKU/재고/관세/배송비 입증 전 금지.

## 7. 코드를 읽는 순서: 누적 교육 커리큘럼

1. \`lib/compiler/consolidation/__tests__/recommend.test.ts\` — 기대 결과를 먼저 읽는다.
2. \`lib/compiler/consolidation/recommend.ts\` — 누락·금지 후보가 왜 제외되는지 이해한다.
3. \`documents/2027/HOME_HUB_AND_CONSOLIDATION_SRS.md\` — 그 결과가 실제 집 배송 업무에서 왜 필요한지 확인한다.
4. 상품 URL 정확한 옵션/제조국/HS 후보 테스트와 구현 읽기.
5. KRW 서비스 수수료/운임/관세 별도 계산, Money 정수 처리 읽기.
6. React 고객 화면 — 순수 엔진 결과를 카드/CTA로 표시하는 방법 학습.
7. Prisma 관계 — 하나의 고객 주문에 여러 국내 택배와 국제 박스 연결하는 방법.
8. Three.js — 장식적 3D는 기존 웰컴 장면 유지; 결제/관세/상태 UI의 정확성과 별개로 학습한다.

**출시 준비의 완료는 '사용자가 코드를 보고 승인'이 아니라, 승인된 실제 데이터로 컴파일러 테스트가 통과하고, 안전한 실거래·통관·환불·추적이 가능한 것**이다.

## 8. 이미지/시각자료 사용 방침

- 저장소의 기존 상품 사진은 출처와 이용허락 여부를 별도로 관리하며, 신규 사업 홍보에 사용할 권리가 있다고 자동 가정하지 않는다.
- 대화에서 비동기 검색으로 표시된 사진은 이미지 파일이 저장소에 존재한다는 의미가 아니며, 해당 원본을 그대로 Git에 재게시할 권리를 뜻하지 않는다.
- 에이전트는 **독자 제작한 SVG 화면 와이어프레임/흐름도**를 \`documents/2027/assets/\`에 커밋하고, 실제 UI 구현 뒤에는 직접 촬영/생성한 테스트 스크린샷을 출처·시나리오와 함께 첨부한다.
- 실제 사용자 PII/집 주소가 들어간 스크린샷은 저장소에 커밋하지 않는다.
